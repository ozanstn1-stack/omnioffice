# Translations (en / tr)

The interface ships in English and Turkish. Both dictionaries are flat JSON
assets under `src/lib/i18n/`; the app fetches the requested one at runtime, so
the files are data, not code, and adding a language means adding a file.

## How a string gets translated

1. Add the key to **both** `src/lib/i18n/en.json` and `src/lib/i18n/tr.json`.
   Keys are dotted namespaces (`health.score`, `petition.saveDocx`), and a
   placeholder is written `{name}` in the value.
2. Use it in the component: `const t = useT();` then `t("health.score")` or
   `t("health.document", { name })`.

The translator falls back to English, then to the raw key, so a missing key is
visible as `some.key` on screen instead of a blank.

## What `npm run i18n:audit -- --check` enforces

The audit runs in the `Lint` job on every push and pull request. It fails when:

- a key exists in `en.json` but not in `tr.json` (or the other way around),
- a component calls `t("…")` with a literal key the table does not have,
- the `{placeholder}` set of a key differs between the two languages — a
  Turkish value missing `{count}` renders the literal `{count}`, or drops the
  number entirely,
- the source has more user-visible JSX text than `scripts/i18n-baseline.json`
  records.

It also fails when:

- a string used through `t.plural("key", n)` has no `key.one` / `key.other` in
  either language,
- any value spells its plural as `(s)` — that is what `t.plural` replaced.

It prints two advisory lines that never fail the build: values that are
identical in both languages (brand names, units and short labels are legitimately
the same) and keys no literal `t("…")` call reaches (keys reached through a
computed name exist and the audit cannot see them).

## Plural forms

A count belongs in `t.plural`, never in a `(s)` suffix:

```ts
t.plural("invoices.duplicatesFound", count, { count })
```

`t.plural` selects the variant through `Intl.PluralRules`, so the same call
renders "1 duplicate invoice found!" / "3 duplicate invoices found!" in English
and "1 adet mükerrer fatura tespit edildi!" / "3 adet …" in Turkish — Turkish
never marks the noun as plural after a numeral, so both variants hold the same
sentence there. Add `key.one` and `key.other` to both dictionaries; a key
without variants falls back to the plain string, which is why `t.plural` is safe
to call for any key.

## Props are measured too

The scanner (`scripts/lib/i18n-jsx.mjs`) counts user-visible text in three
shapes, each with its own baseline section:

| section | what it counts |
| --- | --- |
| `files` | JSX text nodes with at least two letters |
| `attributes` | `alt`, `aria-label`, `title`, `placeholder` values |
| `props` | component `label`, `hint` and `subtitle` values |

A value counts when it is a literal - `label="Save"`, `label={"Save"}` or
``label={`Save`}``. A `t("…")` call, a variable and a template with `${…}` do
not count. **Known gap:** the branches of a conditional
(`label={flag ? "A" : "B"}`) are not measured yet; translate those through a key.

The prop list only holds names a component in this repository really declares:
`label` and `hint` (`Field`, `SectionTitle`) and `subtitle` (`Screen`). A name
is added on purpose, and `src/lib/i18n-jsx-audit.test.ts` pins the list. `title`
is deliberately absent: it is a real JSX attribute, so counting it as a prop
too would report the same text twice. Adding a name changes what is counted,
not the shape of the baseline, so the schema stays at version 3.

`npm run i18n:audit -- --props-report` prints the backlog, one
`file:line<TAB>prop<TAB>text` line per string, cheapest file first - that is the
queue the translation slices work through. Still unmeasured, and counted only
when a slice picks them up: `label:` inside an object literal (`options` arrays),
`title:` fields of toast payloads, and the conditional `subtitle` branches of
`PetitionWizard`.

The six `label` values that remain are the formula names on the Calc ribbon
(`SUM`, `AVERAGE`, `IF`, `COUNT`, `ROUND`, `VLOOKUP`). They are literal by
design: they name spreadsheet functions, not UI prose, exactly like `TRY` and
the `pdf, docx, md` format lists. That is why the prop baseline stops at 6
instead of zero.

## The hardcoded-text ratchet

`scripts/i18n-baseline.json` counts user-visible JSX text nodes per file,
measured with the TypeScript parser, so generics and comparisons (`Map<K, V>`,
`a > b`) are never mistaken for prose. It is a ratchet:

- moving a string into the dictionaries lowers the file's count; re-record it
  with `npm run i18n:audit -- --update`,
- the update refuses to raise a count unless `--allow-raise` is passed on
  purpose, so the diff shows exactly which file grew,
- adding a new file with hardcoded text fails the audit until it is recorded.

When the baseline was first recorded the tree had 131 nodes across 30 files.
`DocumentHealthScreen`, `PetitionWizard`, `Invoices`, `KvkkWizard` and the
thumbnail-size options in `Organize` have moved into the tables (plus five
attribute strings the audit does not measure: the dialog's `aria-label`, the
thumbnail-size label and three `alt="Page N"` texts), taking the baseline to
**80**. Most of what is left is literal by design - `TRY`, the accounting
software names (Luca/Logo/Zirve), paper sizes, units and the `1, 2, 3`
numbering samples - so the number will not reach zero; the real prose still to
move is in `Redact`.

## Attribute strings

The scanner also counts `alt`, `aria-label`, `title` and `placeholder` values
that hold prose, in their own section of `scripts/i18n-baseline.json`
(`attributes`), with the same ratchet. What remains there is literal on purpose:
model ids (`nomic-embed-text`, `deepseek-v4-flash`), prompt examples
(`tr, en, de`), format lists (`pdf, docx, md`), units (`ms`) and the `Bates`
stamp name.

Component props that hold user-visible text (`Field label="…"`,
`Field hint="…"`, `Screen subtitle="…"`) are measured in their own `props`
section, described above. What stays outside is the text that never goes through
a JSX literal: object literals such as `{ value: "employee", label: "Çalışan" }`
and the `description:` strings built in `src/lib/document-health.ts` — the
scanner reads `.tsx` files only.
