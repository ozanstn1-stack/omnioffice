# Translations (en / tr)

The interface ships in English and Turkish. Both dictionaries are flat JSON
assets under `src/lib/i18n/`; the app fetches the requested one at runtime, so
the files are data, not code, and adding a language means adding a file.

## How a string gets translated

1. Add the key to **both** `src/lib/i18n/en.json` and `src/lib/i18n/tr.json`.
   Keys are dotted namespaces (`health.score`, `petition.saveDocx`), and a
   placeholder is written `{name}` in the value.
2. Use it in the component: `const t = useT();` then `t("health.score")` or
   `t("health.document", { name })`.

The translator falls back to English, then to the raw key, so a missing key is
visible as `some.key` on screen instead of a blank.

## What `npm run i18n:audit -- --check` enforces

The audit runs in the `Lint` job on every push and pull request. It fails when:

- a key exists in `en.json` but not in `tr.json` (or the other way around),
- a component calls `t("…")` with a literal key the table does not have,
- the `{placeholder}` set of a key differs between the two languages — a
  Turkish value missing `{count}` renders the literal `{count}`, or drops the
  number entirely,
- the source has more user-visible JSX text than `scripts/i18n-baseline.json`
  records.

It also fails when:

- a string used through `t.plural("key", n)` has no `key.one` / `key.other` in
  either language,
- any value spells its plural as `(s)` — that is what `t.plural` replaced.

It prints two advisory lines that never fail the build: values that are
identical in both languages (brand names, units and short labels are legitimately
the same) and keys no literal `t("…")` call reaches (keys reached through a
computed name exist and the audit cannot see them).

## Plural forms

A count belongs in `t.plural`, never in a `(s)` suffix:

```ts
t.plural("invoices.duplicatesFound", count, { count })
```

`t.plural` selects the variant through `Intl.PluralRules`, so the same call
renders "1 duplicate invoice found!" / "3 duplicate invoices found!" in English
and "1 adet mükerrer fatura tespit edildi!" / "3 adet …" in Turkish — Turkish
never marks the noun as plural after a numeral, so both variants hold the same
sentence there. Add `key.one` and `key.other` to both dictionaries; a key
without variants falls back to the plain string, which is why `t.plural` is safe
to call for any key.

## Props are measured too

The scanner (`scripts/lib/i18n-jsx.mjs`) counts user-visible text in three
shapes, each with its own baseline section:

| section | what it counts |
| --- | --- |
| `files` | JSX text nodes with at least two letters |
| `attributes` | `alt`, `aria-label`, `title`, `placeholder` values |
| `props` | component `label`, `hint` and `subtitle` values |

A value counts when it is a literal - `label="Save"`, `label={"Save"}` or
``label={`Save`}`` - or when it is an expression that reaches the screen: both
branches of a conditional (`label={flag ? "Kaydet" : "İptal"}`), the fallback of
`??`, `||` and `&&`, and the strings inside a template's interpolations. A
`t("…")` call, a variable and a template made only of placeholders do not count.
Two things deliberately stay out: the condition of a conditional (`mode ===
"edit"` is a comparison, not prose) and `+` concatenation (a builder, not a
sentence).

The prop list only holds names a component in this repository really declares:
`label` and `hint` (`Field`, `SectionTitle`) and `subtitle` (`Screen`). A name
is added on purpose, and `src/lib/i18n-jsx-audit.test.ts` pins the list. `title`
is deliberately absent: it is a real JSX attribute, so counting it as a prop
too would report the same text twice. Adding a name changes what is counted,
not the shape of the baseline: adding `hint` and `subtitle` kept it at v3, and
only the new `objects` section below moved the schema to v4.

`npm run i18n:audit -- --props-report` prints the backlog, one
`file:line<TAB>prop<TAB>text` line per string, cheapest file first - that is the
queue the translation slices work through. `--expressions-report` prints only
the strings the wider expression rule added, tagged `branch` (a conditional arm
or a logical fallback) or `span` (inside a template's interpolation), so a
reviewer sees what a measurement grew by instead of trusting the number.

Still unmeasured: a string that arrives through a variable (`const m = "…";
<p>{m}</p>`), a function's return value, and `+` concatenation. None of them is
a literal at the place the user reads it.

The six `label` values that remain are the formula names on the Calc ribbon
(`SUM`, `AVERAGE`, `IF`, `COUNT`, `ROUND`, `VLOOKUP`). They are literal by
design: they name spreadsheet functions, not UI prose, exactly like `TRY` and
the `pdf, docx, md` format lists. That is why the prop baseline stops at 6
instead of zero.

## Object literals and `.ts` modules

The JSX scan reads `.tsx` files only, so interface text that never passes through
a JSX literal stayed invisible: an option list (`{ value: "employee", label:
"Çalışan" }`), a toast title, or a sentence built inside a `.ts` module such as
`src/lib/document-health.ts`. `scanObjects` reads those into their own `objects`
section of `scripts/i18n-baseline.json` (schema **v4**), under the same ratchet
rules as the other sections.

It is deliberately narrow, because a wrong entry costs a translator a string
that never needed translating:

- only keys that hold text are read - `label`, `title`, `description`, `hint`,
  `subtitle`, `placeholder`, `tooltip` and the toast's second line, `detail`.
  `name`, `value` and `message` carry identifiers, product names and developer
  errors.
- only a value with a Turkish-specific letter (`ç ğ ı ö ş ü`) is counted, so a
  product name (`DeepSeek`) or an identifier (`Letter`) stays out. The price is
  stated: ASCII-only Turkish ("Belge") is not caught either - it appears in the
  report's `unmarked` list instead of the baseline.
- a value may be a string, a template (`${…}` collapses to one placeholder) or a
  conditional (each branch counts once). `??`, `||`, `&&` and the strings inside
  a template's interpolation count; concatenation and calls do not.
- `// i18n-content: <reason>` above an entry, or above the declaration that
  holds it, keeps that text out; the report lists every use with its reason. An
  empty reason is ignored, so nothing hides silently.
- a file that writes the document rather than the interface
  (`src/lib/official-letter.ts`, `src/lib/official-letter-template.ts`, the AI
  scoring fixtures) is listed in `CONTENT_PATHS` with its reason in code, so the
  justification goes through review.

`npm run i18n:audit -- --objects-report` prints three lists: what is counted,
what a pragma or a content file keeps out (with the reason), and the unmarked
values the narrow rule let through.

The first record was **34 strings in 7 files**. Turning them into translations
never widens the baseline: the string leaves the file and the section drops with
it. The first slice moved the nine `document-health` findings (the module now
returns `titleKey`/`descriptionKey` plus `params`, and the screen renders
`t(key, params)`) and the KVKK template options, then the toast titles that were
still literals inside `push({ title: … })` calls, taking the section to **0**.
The language picker's table is excluded by a pragma - a language is listed under
its own name - and three files that write documents rather than the interface
are in `CONTENT_PATHS`. A zero here means "nothing left that this scan can see
and that should be translated", not "no text anywhere": the narrow key list and
the Turkish-letter rule still leave ASCII-only Turkish outside, as described
above.

Template attributes joined the scan after the last slice: `alt={`Page ${page}`}`
used to be invisible because only plain strings were read, and two fixed English
words ("Source page", "by") were hiding inside templates. They are translated now,
and the two shortcut hints that remain (`${…} (Ctrl+K)`, `${…} (Shift+F2)`) are
recorded in the attribute baseline, which is why it stands at **11**.

`detail` joined the key list last and found **no** translatable string: every
toast detail is either already a `t(…)` call, a computed value or a version or
count. The gap was worth closing anyway - the next hand-written Turkish detail
fails the audit instead of slipping in - and the measurement is recorded here so
nobody expects a queue that does not exist.

## The hardcoded-text ratchet

`scripts/i18n-baseline.json` counts user-visible JSX text nodes per file,
measured with the TypeScript parser, so generics and comparisons (`Map<K, V>`,
`a > b`) are never mistaken for prose. It is a ratchet:

- moving a string into the dictionaries lowers the file's count; re-record it
  with `npm run i18n:audit -- --update`,
- the update refuses to raise a count unless `--allow-raise` is passed on
  purpose, so the diff shows exactly which file grew,
- adding a new file with hardcoded text fails the audit until it is recorded.
  Note the asymmetry: `--update` will record a file that has **no** baseline
  entry without `--allow-raise`, because the growth guard only compares files
  that are already recorded. That is how a new file joins the ratchet; it is
  also why the raise flag matters only once a file is in the table.

When the baseline was first recorded the tree had 131 nodes across 30 files.
`DocumentHealthScreen`, `PetitionWizard`, `Invoices`, `KvkkWizard` and the
thumbnail-size options in `Organize` have moved into the tables (plus five
attribute strings the audit does not measure: the dialog's `aria-label`, the
thumbnail-size label and three `alt="Page N"` texts), and the vault's paging and
semantic-index labels have left `Vault` too. The KDV1 window's sixteen
hand-written `TRY` suffixes now go through one `money()` helper, which also
rounds to two decimals - the suffix used to inherit `toLocaleString`'s default
of three.

The baseline stands at **50 nodes**: the accounting software names
(Luca/Logo/Zirve), paper sizes, units and the `1, 2, 3` numbering samples are
literal by design, so the number will not reach zero; the real prose still to
move is in `Redact`.

## Attribute strings

The scanner also counts `alt`, `aria-label`, `title` and `placeholder` values
that hold prose, in their own section of `scripts/i18n-baseline.json`
(`attributes`), with the same ratchet. What remains there is literal on purpose:
model ids (`nomic-embed-text`, `deepseek-v4-flash`), prompt examples
(`tr, en, de`), format lists (`pdf, docx, md`), units (`ms`) and the `Bates`
stamp name.

Component props that hold user-visible text (`Field label="…"`,
`Field hint="…"`, `Screen subtitle="…"`) are measured in their own `props`
section, described above. What stays outside is the text that never goes through
a JSX literal: object literals such as `{ value: "employee", label: "Çalışan" }`
and the `description:` strings built in `src/lib/document-health.ts` — the
scanner reads `.tsx` files only.
